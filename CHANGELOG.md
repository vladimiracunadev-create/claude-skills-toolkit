## 🚧 [Unreleased]

### ✨ Añadido

- **`skills/python-lint-guard/` — nuevo skill: el gate de Python que faltaba en la cadena de guardias.** Hasta ahora un `.py` modificado atravesaba `pre-commit-guard` y `pre-push-guard` **sin lint**: ambos encadenaban `yaml-control` + `md-lint-fix` + `pytest` y ninguno miraba el estilo del Python. Su aporte propio **no es correr `ruff`** —eso ya lo hace el CI— sino la capa que ninguna herramienta cubre: la **paridad entre lo declarado y lo ejecutado**. Cruza el toolchain que el repo declara (`pyproject.toml` `[tool.*]` y dependencias, `ruff.toml`, `.ruff.toml`, `setup.cfg`, `.flake8`, `tox.ini`, `.pre-commit-config.yaml`) contra el que el CI realmente ejecuta (`.github/workflows/*.y*ml`, leyendo solo líneas `run:`/`uses:` para no confundir un comentario o el nombre de un job con una ejecución real), y reporta cinco desalineaciones: `PARITY-NO-CI` (declarado sin gate en CI), `PARITY-NO-CONFIG` (el CI corre algo que el repo no declara → el dev no puede reproducir en local lo que el CI exige), `PARITY-CONFLICT` (dos herramientas que **comparten rol**), `PARITY-NO-GATE` (hay `.py` y ningún linter) y `PARITY-HOOK-ABSENT`. Este último es el hallazgo que justifica el skill: un repo puede tener `.pre-commit-config.yaml` correcto y workflow que lo ejecuta, y aun así acumular decenas de commits de arreglo porque **nadie corrió `pre-commit install`** — la configuración existe, la barrera no, y cada violación viaja hasta CI y vuelve como fallo. Ningún linter lo detecta porque no es un problema de código sino de dónde está puesto el gate. El rol de cada herramienta se modela como **conjunto**, no como etiqueta: `ruff` cumple los roles de linter *y* formateador a la vez, y compararlos como cadenas (`"linter+formatter"` vs `"formatter"`) dejaba pasar el conflicto `ruff` + `black`, que es el más frecuente. Capa 2 opt-in con `ruff`: separa las violaciones **mecánicas** (`I001`, `F401`, `UP006`, `UP035`, `W291`, `W293`, `W391`, `RUF100`, `COM812`, `Q000` — únicas que toca `--fix`, vía `ruff check --select <set> --fix`, nunca un `--fix` global) de las que exigen **criterio** (`F841`, `E741`, `E402`, `E501`, `S110`, `S112`, `C901`, `B008`), porque auto-corregir `F841` borra una variable que muchas veces no es basura sino el resultado de una llamada que alguien olvidó comprobar: se elimina el síntoma y queda el bug. Núcleo stdlib; sin `ruff` reporta `RUFF-ABSENT` y entrega igual el análisis de paridad. Triggers: "arregla el lint de Python", "corrige ruff", "por qué falla el lint en CI", "black rompió el CI".

- **`skills/python-deps-pinning/` — nuevo skill: cuantifica la cobertura real del scan de dependencias.** Un scanner de vulnerabilidades responde a "¿la versión X del paquete Y tiene CVEs?"; si el manifest declara `requests` a secas o `requests>=2.0` sin lockfile, no hay versión X que consultar y la dependencia **no sale limpia — es que nunca se miró**. `security-audit` ya era honesto sobre esa limitación pero no la cuantificaba por fichero; este skill convierte el silencio en un número. Clasifica cada dependencia en `exact` (`==1.2.3`), `locked` (rango **+ lockfile en el mismo directorio**), `range`, `bare` y `direct` (URL/VCS/`-e`), y solo las dos primeras cuentan como auditables. Lee `requirements*.txt` (ignorando `-r`, `-c`, `--index-url`, marcadores de entorno y comentarios), `pyproject.toml` en PEP 621, `[dependency-groups]` (PEP 735) y tablas de Poetry; detecta `poetry.lock`, `uv.lock`, `Pipfile.lock`, `pdm.lock` y `requirements.lock`. Dos decisiones deliberadamente conservadoras, porque el error que este skill existe para evitar es justamente inflar la cobertura: `==1.2.*` **no** cuenta como pin (el comodín no fija versión concreta) y un lockfile solo cubre el manifest de **su propio directorio** (un `poetry.lock` en la raíz no se asume válido para el `requirements.txt` de un subproyecto). Solo lectura: da la receta de lockfile del gestor detectado, nunca ejecuta `pip-compile` ni `poetry lock` por su cuenta, porque regenerar un lockfile cambia el árbol de dependencias y esa es decisión del proyecto. Complementa a `security-audit` (le amplía la superficie auditable) y no se solapa con `python-version-control` (ese cubre la versión del intérprete, no la de las deps). Cero deps. `--strict` y `--threshold N` para CI.

- **`skills/version-bump/` — promovido desde `~/.claude/skills/` con `version_probe.py` (397 LOC, stdlib).** El skill existía como **solo instrucciones**: 200 líneas explicándole al agente cómo distinguir un marcador de versión ACTUAL (se bumpea) de una referencia HISTÓRICA (se conserva). Eso funciona hasta que no funciona, y cuando falla lo hace en silencio y de forma irreversible — o la landing sigue anunciando la versión anterior, o se reescribe una entrada de changelog y se rompe la trazabilidad. `version_probe.py` convierte esa regla en código con una propiedad explícita: **no adivina**. Clasifica cada aparición en `ACTUAL`, `HISTORICO` o `AMBIGUO`, y lo ambiguo se marca para revisión humana en vez de resolverse por estadística. Reglas por precedencia: (1) en ficheros `CHANGELOG`/`HISTORY`/`RELEASES`/`NEWS` todo es histórico salvo la sección `Unreleased`; (2) el campo de versión de un manifest es actual por definición; (3) señales **inequívocas** de presente (`shields.io`, `badge/`, `__version__`, `"version":`, `<Version>`, `--version`); (4) señales de pasado (`entregado`, `released in`, `since v`, `added in`); (5) señales débiles de presente (`versión actual`, `en curso`); (6) encabezados —actual en `ROADMAP`/`PLAN`, ambiguo en el resto—. **El orden de (3) sobre (4) no es cosmético**: el patrón `[![Version](https://img.shields.io/badge/version-X-…)](CHANGELOG.md)` aparece en casi todos los repos y contiene la palabra `CHANGELOG` en la URL; sin esa precedencia se clasificaba como historia y el badge quedaba anclado a la versión vieja para siempre — detectado al dogfoodear el probe sobre este mismo repo. `--verify --old X --new Y` es la prueba de fuego automatizada: exit 1 si algún marcador ACTUAL conserva la versión vieja. Además detecta drift entre manifests de la raíz. Agnóstico del stack (Cargo, npm, Python, Go, .NET, Java, o sin gestor).

- **`skills/md-to-doc/` — nuevo skill: árbol de Markdown → documento.** Renderiza `docs/`, ADRs, runbooks o cualquier colección de `.md` a un HTML autocontenido con portada e índice, y opcionalmente a PDF. Ataca dos fallos concretos: (1) **documentos que no son autocontenidos** —un HTML que referencia `./img/x.png` se rompe en cuanto se mueve—, resuelto embebiendo cada imagen como **data URI con `base64` de la stdlib**, sin dependencias; (2) **diagramas que desaparecen al exportar**: GitHub renderiza los fences ` ```mermaid ` de forma nativa, así que se escriben sin pensarlo, pero al pasar a PDF no los renderiza nadie y el diagrama sale como texto plano. Arquitectura por capas calcada de `security-audit`: el núcleo **nunca** depende de nada externo (parseo de encabezados, párrafos, énfasis, código, listas, tablas, citas, reglas, enlaces e imágenes; orden por `--order` → `SUMMARY.md` → prefijo numérico → alfabético) y cada capa se pide explícitamente y degrada con aviso impreso **en el propio documento**: `images` (Pillow), `highlight` (pygments), `diagrams` (`mmdc`, con **caché por `sha256` del diagrama** — importa porque `mmdc` arranca un Chromium por invocación), `exec` y `pdf` (xhtml2pdf). La capa `exec` ejecuta bloques marcados ` ```lang run ` y **captura su salida real**, de modo que la documentación no puede quedar desincronizada del código que documenta; está desactivada por defecto, avisa por `stderr`, corre con `python -I` (aislado de `PYTHONPATH` y del `site` del usuario) y con timeout configurable, y su límite se documenta sin adornos: ejecuta código del Markdown de origen, así que solo debe usarse sobre fuentes de confianza. Verificado extremo a extremo sobre los 40 `.md` de este repo (29 bloques mermaid, 80 tablas, 180 bloques de código) y con PDF real de salida.

- **`tests/test_new_skills.py` — 31 tests funcionales de los cuatro skills nuevos** (total: 17 → **48**). Cubren la lógica de decisión, que es donde una regla mal aplicada hace daño real: que `MECHANICAL` y `JUDGMENT` sean disjuntos y que `F841`/`E402`/`S110`/`C901` **nunca** entren en el set auto-corregible; que `==1.2.*` no cuente como pin y que un rango sin lockfile no cuente como auditable; que un badge que enlaza al CHANGELOG se clasifique como ACTUAL; que lo ambiguo se reporte como ambiguo en vez de adivinarse; y que la capa `exec` de `md-to-doc` esté apagada por defecto. El cargador de módulos registra el módulo en `sys.modules` **antes** de `exec_module` porque los scripts combinan `from __future__ import annotations` con `@dataclass`, y `dataclasses` resuelve las anotaciones diferidas mirando `sys.modules[cls.__module__]`.

- **`repo-coherence-audit`: dos dimensiones nuevas — encoding (mojibake) y metadatos del remoto.** (1) **Encoding**: nuevo `scripts/mojibake_probe.py` (146 LOC, solo stdlib) que detecta y repara texto degradado por decodificación errónea (UTF-8 leído como cp1252 y re-guardado: `más` → `mÃ¡s`, `🛡️` → `ðŸ›¡ï¸`). Detección por **round-trip programático**, nunca por `grep 'Ã'` — el patrón no-ASCII se corrompe en tránsito por el shell y matchea los bytes del texto *sano* (`Ã`→`C3` = toda vocal acentuada), dando falsos positivos masivos en ficheros impecables. Reparación con mapa **sloppy-cp1252** (cp1252 + latin-1 en los 5 bytes `81 8D 8F 90 9D` que cp1252 deja sin definir): con cp1252 puro los emoji lanzan `UnicodeEncodeError` y quedan rotos *en silencio* mientras los acentos sí se corrigen. Repara hasta punto fijo (doble capa de mojibake), preserva el conteo de líneas por invariante, y tras `--fix` re-verifica del disco con `residual = 0` (exit 1 si no). Verificación documentada por hexdump/`unicode_escape` — si stdout es cp1252, el `print` del texto reparado lo re-mangla y "parece" que la reparación rompió algo que está bien. (2) **Metadatos del remoto**: el "About" de GitHub (description, homepage, topics vía `gh api repos/<owner>/<repo>`) no vive en el repo — ningún `grep` local lo alcanza y ninguna review de PR lo mira, así que queda stale con impunidad siendo lo primero que lee quien llega. Se contrasta contra las mismas fuentes de verdad y se corrige con JSON + `--input` (nunca texto no-ASCII por el shell, que puede *introducir* mojibake al arreglar los conteos), verificando releyendo de la API. SKILL.md suma 6 errores comunes nuevos (#8–#13) y README del skill actualizado con ambas dimensiones.

- **`skills/repo-coherence-audit/` — nuevo skill: reconcilia docs↔repo.** Audita lo que la documentación y el código *afirman* (versión, conteo de tests, conteo/enumeración de workflows, pins de acciones a SHA, prerequisitos Node/Python) contra *fuentes de verdad verificables*. Trae `scripts/coherence_probe.py` (243 LOC, solo stdlib): de una sola pasada reúne versiones de todos los manifests (`package.json`/`pyproject.toml`/`Cargo.toml`/`VERSION`/`__version__`, con detección de drift si conviven distintas), la lista+conteo real de workflows (`ls .github/workflows/`), el conteo de tests (`pytest --collect-only` best-effort por stack) y los `uses: …@<sha>` reales. El eje del skill es el **Principio #1 — ACTUAL vs HISTÓRICO**: distingue el marcador de estado que se sincroniza a la verdad (título de doc, `version` de otro manifest, `# N tests` junto a un comando, tabla de "SHAs activos") de la referencia histórica que se conserva (entradas de CHANGELOG, secciones de ROADMAP por versión, "22 → 49 tests" narrando una evolución). Modo **report** por defecto (solo diagnostica, `afirma X · real Y · fichero:línea`); modo **fix** opt-in con correcciones acotadas por fichero/línea (nunca `sed` global). Excluye vendor y worktrees de `.claude` para no contaminar el drift. Delega en un flujo de version-bump cuando la conclusión es *publicar* un release (elegir semver, taggear, checksums), no solo alinear marcadores. Complementa a `python-version-control` (ese audita la versión del intérprete; este, versión de release + conteos + workflows). Triggers: "audita coherencia", "revisa que los docs cuadren", "los conteos no cuadran", "el README dice X pero el repo tiene Y", "drift de docs". Cero deps (`pytest` opt-in solo para el conteo). Segundo hito de v0.3.0.

- **`security-audit`: reporte de cobertura real del scan.** Nueva función `compute_coverage()` que compara lo *declarado* en cada manifest contra lo que los parsers *realmente escanearon*, y hace el gap explícito en tres lugares: (1) warning en consola (`⚠ Cobertura: N deps FUERA del scan`), (2) línea de % de cobertura en el resumen ejecutivo del reporte, (3) sección "🔍 Cobertura del scan de dependencias" con tabla `dep | spec | archivo:línea | motivo`. Detecta: deps PyPI sin pin exacto (`flask>=2.0`, `pandas`), editable installs y URLs en `requirements*.txt`, deps de `pyproject.toml` (PEP 621 + Poetry, parseadas con `tomllib`) no capturadas por el scanner, `package.json` sin `package-lock.json`, `go.mod` sin `go.sum`, `Cargo.toml` sin `Cargo.lock`. Caso extremo endurecido: si NINGUNA dep es escaneable pero hay declaradas, ahora sale exit 1 con aviso claro (antes: exit 0 con "No se detectaron manifests", engañoso). Motivación: un reporte "0 vulnerabilidades" con 2 de 3 deps sin escanear daba falsa sensación de seguridad — ahora el reporte confiesa "0 vulnerabilidades en el 33% que pude revisar". Cambio 100% aditivo: `coverage` es kwarg opcional de `build_report()`, el scan y los exit codes existentes no cambian. Incluye `tests/test_security_audit_coverage.py` (8 tests happy-path — primer test funcional por skill, adelanta el item de v0.3.0).

- **`README.md` profesional en cada skill** (9 archivos, uno por skill de producción). Cada uno cubre: qué hace (con diagrama Mermaid), triggers de activación, instalación (vía toolkit installer o standalone desde release), uso con tabla de flags, casos de uso reales con outputs esperados, cómo funciona por dentro, dependencias, limitaciones y skills relacionados. Enlazados desde el catálogo del README principal (`skills/<name>/README.md` en lugar de `skills/<name>/`). Test estructural nuevo `test_each_skill_has_readme_md` que verifica presencia, longitud mínima y secciones obligatorias. Sección "Anatomía de un skill" del README principal actualizada para reflejar que README.md ahora es obligatorio junto con SKILL.md (dos archivos, dos audiencias: contrato-agente vs docs-humanos).
- `skills/pre-commit-guard/` — nuevo skill: gemelo rápido de `pre-push-guard` sobre archivos **staged**. Corre `yaml-control` + `md-lint-fix --dry-run` sobre `git diff --cached --name-only --diff-filter=ACMR` antes de cada `git commit`, con reporte unificado y fail-fast. Objetivo de tiempo < 2s — no corre pytest (los tests pesados quedan para `pre-push-guard`). Soporta `--install-hook` / `--uninstall-hook` para registrarse como git `pre-commit` hook (opt-in, backup automático de hook previo como `.pre-commit.bak`). Cierra el item `pre-commit hook configurable` del ROADMAP v0.3.0. **Justificación:** hasta ahora un YAML roto o Markdown malformado entraba al historial local y forzaba `git commit --amend`/rebase; con este skill el commit se aborta antes. Complementa a `pre-push-guard` sin solaparse (dos capas de defensa: rápida por commit / completa por push). Triggers: "valida antes de commitear", "pre-commit", "guard antes de commit", "instala pre-commit hook".
- `skills/_template/README.md` — esqueleto nuevo con las secciones obligatorias (🎯/📦/🚀), para que cada skill nuevo parta con la estructura que exigen los tests.

Antes, un repo sin manifests hacía return temprano con "No se detectaron manifests" y se saltaba TODAS las capas — incluso las que auditan el repo en sí (Bandit sobre el código propio, gitleaks sobre el histórico, zizmor sobre workflows). Ambos degradan con `⊘` si el skill no está instalado, igual que ya hacían con `yaml-control` y `md-lint-fix`. `partition()` de `pre-commit-guard` gana el bucket `py`, que antes no existía.

## 🎉 [0.2.0] — 2026-07-01

### ✨ Añadido (highlight)

- `skills/python-version-control/` — nuevo skill: audita drift de versión de Python entre 12+ fuentes de verdad. Primer hito de v0.2.0.
- `.github/workflows/release.yml` — automatiza publicación de releases: al pushear un tag `v*` empaqueta cada skill como zip individual + un bundle completo del toolkit y crea el GitHub Release con notas extraídas del CHANGELOG.

### 🛡️ Seguridad

- Migración de `npm` → `pnpm v11` para `md-lint-fix` y CI. Razón: campaña Shai-Hulud en npm (sept 2025 – mayo 2026, 700+ paquetes comprometidos, 14 000 secretos filtrados). pnpm v11 trae postinstall scripts bloqueados por defecto y `minimumReleaseAge=24h` — habría bloqueado todas las oleadas conocidas sin configuración. Documentado en `docs/supply-chain-security.md` con fuentes (CISA, Microsoft, Unit 42, Snyk).

### ✨ Añadido
